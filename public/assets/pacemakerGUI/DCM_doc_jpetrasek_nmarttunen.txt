2: DCM 
The Device Controller-Monitor (DCM) is the user interface for the pacemaker. The DCM 

allows for users to view and modify parameters to fine tune the operation of the patient’s 
pacemaker. Users can additionally request electrocardiograms from the pacemaker. 

 
2.1: DCM Hardware Hiding 

The DCM is currently a software application that interfaces with a pacemaker via USB 
serial communications. Hardware hiding is implemented by compartmentalizing the tasks of 
reading and writing to the serial bus. These functions are then called by higher level functions 
that can interpret and parse the byte data into the appropriate datatype.  

 
2.2: DCM Software Decisions 

The DCM software decisions consist of requirements and design decisions. The 
requirements are compiled from external resources on pacemaker DCM functionality. The design 
decisions are then extracted from the requirements to create the best product possible for this 
application.   

 
2.2.1: DCM Requirements 

The essential aspects of the DCM user interface are the capability of utilizing windows 
for display graphics and text, processing input fields and buttons, and displaying all 
programmable parameters for review and modification. Additionally, there is a label that 
displays what pacing mode is actively selected, and the active pacing mode can be changed upon 
the user’s request. A logout button needs to be provided, which allows the user to return to the 
welcome screen login with different credentials. Labels that display properties about the DCM 
software, such as the current application revision number and institution need to be provided and 
easily accessible. 

The first requirement for the DCM is to have a welcome screen, which is the first 
interface a user sees when they open the program. The welcome screen prompts the user to enter 
a username and password. The user can choose to register the username and password entered 
within the DCM and login as said user. The DCM can store a maximum of 10 users locally. 
After the user logs into the DCM, the application transitions to a new user interface that contains 
all main aspects of the DCM user interface. 

Located in an easy to view and access window, input fields and labels for all required 
programable parameters need to be provided. These entries and labels display the following 
programmable parameters for review and modification: Lower Rate Limit, Upper Rate Limit, 
Atrial Amplitude, Atrial Pulse Width, Ventricular Amplitude, Ventricular Pulse Width, VRP, 
ARP, Max Sensor Rate, Reaction Time, Response Factor, Recovery Time, and Threshold. The 
parameters must also show what units are being used to which are currently editable are changed 



by the pacing mode selection buttons. The user interface presents AOO, AAI, VOO, VVI, 
AOOR, AAIR, VOOR, and VVIR pacing modes. 

A save button needs to be provided for the user to set, store and transmit the currently 
active pacing mode and parameter values locally. This data is associated with the user’s login 
credentials. When the user logs in with the same username and password, the previously saved 
pacing mode and parameter values are loaded and displayed. 

There must be a button which functions as the transition to an alternate screen which 
allows for serial communication between the DCM and the pacemaker board. On this screen, 
there must be a method to link the DCM to the pacemaker board. Additionally, once the board is 
linked to the DCM there must be options to send parameter data from the locally saved 
parameters in the DCM to the pacemaker board.  

In addition to sending parameter data from the DCM to the pacemaker board, there must 
also be a method present to receive and show data from the pacemaker board to the DCM. This 
presentation needs both ventricle and atrium data present and must be able to display the latest 
Egram data available at the will of the user. 

Finally, the parameters need to originate at the DCM and implement through to the 
device in the process outlined above. The parameters need to be stored in a data type that is 
friendly with the memory provided in the Simulink model, but also must be precise enough to 
meet the tolerances provided to us in PACEMAKER. The parameter data is stored using doubles 
for their great precision and ease of use. The memory usage is higher than ints or floats, but the 
Simulink model does not need to waste memory usage on conversions from another data type 
like singles to something usable by the model. 
 
2.2.2: DCM Design Decisions 

The design decisions for the DCM GUI revolve around enhancing user experience by 
clearly defining each programmable parameter and showing changes depending on user 
navigation. For this reason, the DCM uses Python as the development language because Python 
is a high-level language which includes many quality-of-life features compared to other lower-
level languages. Also, the development process in Python is relatively straightforward with easy 
implementation and includes vast documentation and libraries. To display the GUI, Python’s 
Tkinter GUI library is used, as Tkinter is a highly adaptable and widely utilized library with 
extensive documentation and support. Python is also beneficial for backend features, and the 
JSON library is used for saving the user data to a local file. JSON files are advantageous 
compared to other options because the JSON format can be easily converted to Python 
dictionaries, easing implementation. Additionally, the PySerial library is used for communication 
between the DCM and the pacemaker. The PySerial library handles many of the details with 
serial communication, both easing implementation and aiding in hardware hiding. 

The layout of the welcome screen begins with a friendly greeting which prompts the user 
to enter their username and password. Small decisions such as the order of elements, fonts, and 



color are all contributing to the idea of familiarity and convention, ensuring a smooth user 
experience. Some specific examples on the Welcome Screen include the placement of the 
username and password entry widgets and the placement of the login and create new user 
buttons. 

After the user has logged in, they are presented with a grid format of programmable 
parameters. This format was chosen for its effective use of the square window and ease of 
discerning each different parameter. It was also convenient to use this grid format since many of 
the parameters are exact mirrors of each other, allowing for easy substitution. An example of this 
is Atrial Sensitivity which is in the exact same position on the grid as Ventricular Sensitivity and 
vice versa. 

When a new user is created, each of the programmable parameter's defaults to the 
nominal values which are chosen to serve as a reference point. Additionally, the parameter labels 
hold essential information such as the units of measurement which inform the user about the 
values they are adjusting. Finally, if the user inputs a value that is outside the range or invalid for 
what the entry is looking for, an error message is thrown, explaining what went wrong. 

Using the nominal values for inputs on startup is a thoughtful design decision that 
provides users with initial reference points, easing the process of customization. Meanwhile, the 
presence of units in the parameter labels enhances communication and ensures that users are 
well-informed about the values they are adjusting. Additionally, if the user were to enter an 
invalid value, an error message would appear and list the range of acceptable values. 

To select the desired pacing mode, another grid format is utilized for its space efficiency. 
This layout not only optimizes space but also facilitates the placement of the save button, 
positioning it in the last column beside the pacing modes. Additionally, there is a send button 
located directly below the save button which saves the parameters and pacing mode locally, as 
well as serves as the gateway to the E-gram menu. 

The active pacing mode is displayed in the top left corner of the page. The label has 
increased font size and weight to highlight the crucial information and make pacing mode 
changes more apparent to the user. This decision contributes to an interface that is both visually 
appealing and user-friendly. In the top right corner, the logout button allows for users to return to 
the welcome screen and login with different credentials without closing the entire application. 
All of these design decisions collectively contribute to an intuitive, visually appealing, and user-
friendly GUI for the programmable pacemaker, enhancing the overall experience for medical 
professionals and ensuring efficient management of device settings. 

To communicate with the pacemaker, a serial communications window was created 
which includes functionality to connect to the pacemaker, send programmable parameter data, 
and request and view electrocardiogram data from the pacemaker. The pacemaker is 
automatically detected when connected via USB and the “Link” button is pressed and is 
constantly being monitored for an active connection status. Once a pacemaker is connected, the 
user can send the saved programmable parameters to the pacemaker. If the transmission was 
successful, including the checksum passing, a success message is displayed, otherwise an error is 



raised. The user can also request electrocardiogram data, where the pacemaker captures and 
sends two seconds with of data from the atrial and ventricular voltage levels. A time of two 
seconds was chosen because with the slowest pulse rate of 30 BPM, a pulse is guaranteed to be 
captured within the two second window. 

The module structure was given significant thought during the design process. The design 
choice for the project to use many python files organizes the project to make it more modular 
and friendly for multiple people to work on it. The frontend GUI is divided into files that 
represent different pages in the GUI or serve a unique function. The files that tie all these files 
together is the global vars and GUI Helpers files which contain functions and constants that are 
universal for the entire frontend. 

Another design decision with the interface between the GUI and the backend is that the 
interface will contain all the error handling, sending error messages back to the GUI to present to 
the user. This decision additionally aids in separation of concerns, where the lower-level 
modules in the backend can raise errors, the interface can catch and handle the errors, and the 
GUI can perform the appropriate action to display the error to the user. 

 
  



2.1.3: Likely Changes to Requirements and Design Decisions 
Looking ahead, one set of requirements that will be added is the implementation of the 

dual chamber pacing modes. This includes implementing the AV delay parameter which delays 
the pulse to each chamber. Additional pacing mode buttons would need to be added for the dual 
chamber pacing modes, and an additional parameter would need to be added. Serial 
communications would need to be considered when transmitting the new pacing modes and 
parameters.  

Another next step would be to make the pacemaker GUI compatible with multiple 
pacemakers at once and allow the software enough flexibility to switch between the two boards 
at will. Additionally, the DCM should have a secondary, more condensed, design in the scenario 
where there are too many parameters to show at once.  

Additional requirements that are outlined in the PACEMAKER 2007 document from 
Boston Scientific which we did not implement in this model include the following: 

- Language support for the following languages: Danish, Dutch, French, German, Spanish, 
Italian, and Swedish.  

- Visual indication of when telemetry is lost due to device being out of range or an excess 
of noise.  

- The DCM must be capable of visually indicating when a different Pacemaker device is 
approaching than was previously communicated with 

- Set clock function 
- Printed reports of all kinds 

o Though this model can export Egram data as a png 
- Real-time continuous display of Egram data 
- DCM-PG Telemetry

_users: list[User]

object is found, validate the password matches the password belonging to the User object. 
If all conditions are met, return true, otherwise returns false along with a descriptive error 
message for the GUI. 

registerUser(username: str, password: str): tuple[bool, str]

lengrh is below the constant. Verifies the username and password string inputs are 
acceptable by calling _validateUsernameAndPasswordInputs function. If the username 
and password are valid, attempt find the User object with the matching username with the 
_findUser function. If a User object is not found, create a new user object with the given 
username and password, append the object to the _users list and update the local storage. 
If all conditions are met and all operations were successful return true, otherwise return 
false along with a descriptive error message for the GUI.

User objects match, return null.

2.4: DCM Testing 
Testing of the DCM was completed in stages of the development cycle. Initial testing was 

completed on subsets of functions, then modules were individually tested. Once modules were 
initially tested, integration testing was performed where higher level and larger scoped tests were 
completed. There are three parts of the DCM that needed to be rigorously tested for all kinds of 
inputs and scenarios since the types of operations performed are open to much error. 
The username and password entry fields are subject to any input the keyboard can produce. This 
means there are limitless combinations of usernames and passwords that can be inputted. The 
strings inputs must be validated such that they are all valid usernames and passwords before they 
are saved so users are accessible for the user of the DCM. Additionally, with the limitation of 10 
users at once, there is a hard limit of the number of users that can be saved locally. 

Correspondingly, upon logging in, verification to check that the inputs of the parameter 
input fields are all valid numbers and comply to the specific ranges set to the specific parameter 
being measured. This is for the patient’s safety and is designed in a way that the error should be 
caught before being saved locally and sent to the pacemaker. 

Finally, the DCM must be connected to one board at a time and must be capable of 
detecting and updating the connection status of the pacemaker board to the DCM. The DCM 
must constantly be checking if the connection is sustained and must notify the user if the board is 
not connected or if the connection is lost after a pacemaker connects to the DCM. 

The DCM testing aims to take the DCM to its very limit and test all aspects of the 
workflow to ensure the user never gets stuck or inputs a value that they are not supposed to. This 
testing process reassures the DCM is safe and reliable.
